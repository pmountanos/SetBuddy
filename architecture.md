# Architecture

Set Buddy is a single React Native app (Expo, TypeScript) for iPhone and Android. All application code is in `mobile/`. This document explains how it is organised and why; `requirements.md` says what it must do.

## Stack
- **Expo SDK 58** on **React Native 0.88**, React 19, TypeScript in strict mode.
- **Expo Router** for navigation, with native tabs.
- **expo-sqlite** for storage (synchronous API).
- **expo-notifications** for local daily reminders; **expo-document-picker**, **expo-sharing** and **expo-file-system** for spreadsheet import and export.
- **fflate** for reading and writing the zip container of `.xlsx` files. There is no spreadsheet library: the app reads and writes the few XML parts it needs itself.
- **Jest** with **better-sqlite3** for tests, which run in Node against a real SQLite.

The native `ios/` and `android/` folders are generated by `expo prebuild` and are not committed. Anything native is configured through `app.json`, `app.config.js` and config plugins.

## Layout
```
mobile/
  app.json, app.config.js   static config, plus the Apple team ID injected from outside git
  plugins/                  config plugin: Android release signing
  assets/                   app icons
  src/
    domain/                 pure logic, no I/O
    data/                   SQLite schema, repositories, first-launch import of older apps' data
    xlsx/                   reading .xlsx workbooks
    export/                 writing .xlsx and .csv
    notifications/          planning and scheduling the daily reminder
    settings/               small preferences; file picking and sharing
    state/                  app-wide React context
    ui/                     shared components and the larger screen pieces
    app/                    Expo Router routes (the screens)
scripts/                    device build scripts
build/                      export-option templates (tracked) and build outputs (ignored)
```
Imports use the `@/` alias for `mobile/src/`.

## Layers
Dependencies point one way: **screens → state → data → domain**.

### `domain/` — pure logic
No database, no React, no platform APIs, so it is trivially testable.
- `calendarDate.ts` — a calendar day (`{year, month, day}`) independent of time and time zone; date arithmetic is done in UTC so daylight-saving changes cannot skip a day.
- `schedule.ts` — `DayPlan` (rest, or a specific workout), `ProgramCalendarSchedule`, and `todayScheduleStatus`.
- `volume.ts` — set and total volume.
- `workoutDisplaySort.ts` — ordering of workouts: stored `sortOrder` first, then a Push/Pull/Legs naming heuristic as a tie-break.
- `carryoverMatcher.ts`, `stringSimilarity.ts` — matching a new workbook's exercises to the existing program's by name.
- `exerciseKind.ts` — `'strength' | 'cardio'`.

### `data/` — storage
- `db.ts` defines a five-method synchronous interface, `Db` (`exec`, `run`, `all`, `first`, `transaction`). Everything in the data layer talks to that, not to expo-sqlite. `expoDb.ts` adapts expo-sqlite to it; tests adapt better-sqlite3 (`__tests__/testDb.ts`). This is what lets the repositories and importers run unchanged in Node.
- `schema.ts` holds the table definitions, the schema version (`PRAGMA user_version`, currently **2**) and forward migrations. `prepareDatabase` creates or upgrades a database and refuses one from a newer build.
- Repositories, each a class taking a `Db` and an `Env`:
  - `programRepository.ts` — the program, workouts, exercises and schedule, including the schedule cascade.
  - `sessionRepository.ts` — starting, resuming, logging, finishing and reopening a workout session; reference-value lookup.
  - `historyRepository.ts` — completed sessions and their detail.
  - `outlineRepository.ts` — read models for the Program tab and exports.
- `programImporter.ts` — replaces the program from a parsed workbook, in one transaction.
- `models.ts` — row types, their mapped forms, and `Env`: the injected source of new ids, the current time and "today", so tests control all three.

### Tables
| Table | Holds |
|---|---|
| `Program` | The program. The oldest row is the active one; there is normally exactly one. |
| `Workout` | A workout template, with `sortOrder` for display. |
| `Exercise` | An exercise in a workout: name, order, set count, note, per-side flag, kind. |
| `ScheduleEntry` | One row per calendar day: rest, or a workout id. Unique per program and day. |
| `WorkoutSession` | One performance of a workout on a scheduled day; in progress or complete. |
| `LoggedSet` | One set in a session: weight, reps, cardio minutes, max heart rate, and whether the user entered it. |

Deleting a program cascades to its workouts, exercises and schedule. Sessions are deliberately **not** tied to workouts by a foreign key: history must survive the program being replaced, which is why a session stores a snapshot of its workout's title when it is completed. Ids are UUID strings; times are epoch milliseconds.

### `state/` — application state
`AppContext.tsx` opens the database once at startup and provides the repositories to every screen. It also carries a **version counter**: any code that writes calls `refresh()`, and screens read through `useData(...)`, which re-reads when the counter changes. Data volumes are tiny and reads are synchronous, so this replaces a cache or store library with something that cannot go stale. Tabs also call `refresh()` when they gain focus.

### `app/` and `ui/` — screens
`app/_layout.tsx` shows a loading or error screen until the database is open, then a stack containing the tabs and the History detail route. `app/(tabs)/` holds Today, Workout, Program, History and Settings. Larger pieces live in `ui/`: `WorkoutLogger`, `WorkoutEditor`, `ImportStaging`, and `kit.tsx` (buttons, cards, the option sheet used in place of pull-down menus, the text prompt). `theme.ts` supplies light and dark colours.

## How the important things work

### Startup, and upgrading from the earlier native apps
`data/appDatabase.ts` opens `setbuddy.db`. The first launch after upgrading from one of the earlier native apps also brings its data across:
- **Android:** the Kotlin app's `databases/setbuddy.db` has the same schema (this app's schema and version numbers were chosen to match it), so the file and its sidecars are copied into place and migrated forward like any other database.
- **iOS:** the SwiftData store at `Library/Application Support/default.store` is copied together with its `-wal` and `-shm` files (recent writes live there), opened as plain SQLite, and imported by `legacy/swiftDataStore.ts` in one transaction. That file documents the Core Data layout it reads: `ZPERSISTED…` tables, UUIDs as 16-byte blobs, dates as seconds since 2001.

The old files are only read. If the iOS import fails, the new database is deleted so the next launch retries rather than starting empty. On iOS the old reminder setting is also carried over from `UserDefaults`.

### Logging a workout
Opening the logger gets or creates the in-progress session for that workout and day, and makes sure it has one `LoggedSet` row per set in the template. Each field **writes to the database on every keystroke**. An earlier design committed on blur and lost values, because the order of focus and blur events differs between platforms and on Android hiding the keyboard does not end editing. Storing as typed removes the dependency entirely and makes an interrupted session resumable for free.

A row is marked as entered the first time it is written. Touching a set and leaving it confirms the reference values. Finishing deletes rows that were never entered or were cleared back to zero, snapshots the workout title, and marks the session complete. Reopening simply clears the completion; the dropped rows are recreated the next time the logger opens.

### Reference values
`mostRecentLoggedValuesByExercise` walks completed sessions newest-first and keeps the first value seen for each exercise and set index. The lookup is by **exercise id** across all workouts, which is why import carry-over works by preserving ids.

### The schedule cascade
`setScheduleDayShiftingFollowing(day, plan)` first reads the plan for every day from `day` to the horizon. If `plan` already occurs within the next 60 days, only the window up to that occurrence rotates, so the rest of the cycle is untouched. Otherwise `plan` is inserted and every later day moves one day later. Choosing the plan a day already has does nothing. "Add a rest day" forces the insert behaviour.

### Import
`xlsx/readWorkbook.ts` unzips the file; `miniSax.ts` is a small event-style XML reader; `programXlsxParser.ts` turns the workbook, relationship, shared-string and sheet parts into a list of days, each with its exercises. `ui/ImportStaging.tsx` then collects the cycle start, the calendar start and the carry-over choices, and `programImporter.ts` replaces the program. A workout's `sortOrder` is its first position in the workbook, so workouts list in rotation order.

### Export
`export/spreadsheet.ts` writes the smallest valid `.xlsx` (inline strings, no styles) and CSV. `programExport.ts` and `historyExport.ts` build the rows. `settings/importExport.ts` writes a temporary file, opens the share sheet, and deletes the file afterwards.

### Reminders
`notifications/reminderPlan.ts` is pure: given the schedule, the chosen time and "now", it returns the reminders that should be pending. `reminders.ts` cancels everything pending and schedules that plan, skipping the work when the plan has not changed. It runs shortly after any data change and when the app returns to the foreground, which is also what rolls the 14-day window forward.

## Tests and checks
Run from `mobile/`:
```
npx jest            # unit tests, in Node against real SQLite
npx tsc --noEmit    # typecheck
npx expo lint       # lint
npx expo-doctor     # dependency and config health
```
Tests cover the domain logic, schema creation and migration, every repository, the SwiftData importer, spreadsheet import against two real workbooks in `src/xlsx/__tests__/fixtures/`, both exports (including a round trip back through the importer), and reminder planning. One optional test imports a real SwiftData store when `SETBUDDY_REAL_STORE` points at one. There are no automated UI tests; screens have been exercised by hand on the Android emulator and on an iPhone.

## Building
| Goal | Command |
|---|---|
| iOS simulator | `cd mobile && npx expo run:ios --configuration Release --device "iPhone 17" --no-bundler` |
| iPhone (`.ipa`) | `./scripts/archive_mobile_ios.sh` |
| Android (signed `.apk`) | `./scripts/build_mobile_android.sh` |

Version numbers are set by hand in `mobile/app.json` (`version`, `ios.buildNumber`, `android.versionCode`).

### Signing, and what is kept out of git
- **Apple team ID.** Not in any tracked file. `mobile/app.config.js` and `scripts/apple_team.sh` read it from the `APPLE_TEAM_ID` environment variable or from `signing.local.env` at the repo root, which is gitignored; `signing.local.env.example` shows the format. The tracked `build/ExportOptions-*.plist` files omit the team, and the scripts add it to a temporary copy.
- **Android keystore.** `keystore/` and `keystore.properties` are gitignored. `mobile/plugins/withReleaseSigning.js` wires them into the generated Gradle project; without them a release build falls back to the debug key. `scripts/generate_release_keystore.sh` creates a new keystore.

### Constraints that will bite
- **Expo SDK 58 or later is required with Xcode 27.** Apps built against the iOS 27 SDK must adopt the scene lifecycle, which earlier SDKs do not. The project is on the SDK 58 pre-release, and `mobile/.npmrc` relaxes npm's peer-dependency checks because of it; both should be revisited when SDK 58 is stable.
- **The repo path must not contain a space.** Expo's native build scripts do not quote paths.
- **Changing the schema** means adding a migration to `MIGRATIONS` in `data/schema.ts` and bumping `SCHEMA_VERSION`; existing installs depend on it.

## History
Set Buddy began in March 2026 as a native SwiftUI and SwiftData iPhone app; an Android app in Kotlin (Compose, with a Kotlin Multiplatform shared module) followed in September 2026. Both were replaced by this React Native app on 2026-10-05 and removed from the repository. The last commit containing them is the parent of "Retire the native iOS and Android projects". `development_plan.md` has the fuller story.
